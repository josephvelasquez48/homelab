# Home VPN

WireGuard on the Pi, so phones and laptops can open `https://cam.home`
away from home ([cam.md](cam.md), phase 3). Not on the original roadmap.

```
phone (cellular, anywhere) ──UDP 51821──► router ──► Pi: wg0, 10.8.0.1
                                                       ├─ DNS (cam.home → Pi)
                                                       ├─ Traefik → cam app (sign-in, WebRTC setup)
                                                       └─ forwarded + NATed → Mac UDP 8189 (the video)
```

## What a VPN device can reach

**Only the camera**, on purpose: the Pi (DNS, and Traefik for `cam.home`)
and the Mac's WebRTC port. Not the rest of the LAN, not SSH, not the other
`.home` sites' backends beyond Traefik. It's a split tunnel - only those
two addresses go through it; everything else on the phone uses its own
connection as normal. DNS goes to the Pi while the VPN is on, so
`cam.home` resolves (and the phone gets the home ad blocking too).

Widening it means changing both `wireguard_client_allowed_ips`
(`roles/wireguard`, what phones send into the tunnel) and the firewall
role's forwarding rule (what the Pi lets through), then re-adding phones
so they pick up the new AllowedIPs.

## Pieces

| Where | What |
|---|---|
| `ansible/roles/wireguard/` | `wg0` (10.8.0.1/24, UDP 51821), server key generated on the Pi, `wg-peer` |
| `ansible/roles/firewall/` | ufw: 51821/udp from anywhere; DNS from 10.8.0.0/24; forward 10.8.0.0/24 → Mac 8189/udp |
| `ansible/group_vars/pi.yml` | Port, subnet, interface and the Mac's address, shared by both roles |
| `kubernetes/argocd/traefik-security.yaml` | Traefik's NetworkPolicy admits 10.8.0.0/24 (applied by hand) |
| Router | Port forward UDP 51821 → 192.168.1.253 |

- **Port 51821, not 51820**: K3s's flannel already uses 51820 for its own
  WireGuard between the nodes (`flannel-wg`).
- **NAT to the Mac**: VPN traffic to the Mac leaves the Pi masqueraded as
  192.168.1.253 (a PostUp rule in `wg0.conf`), since the Mac's replies go
  to its default route - the router - which doesn't know 10.8.0.0/24.
- **Traefik needed its own rule**: K3s's iptables chains handle :443
  before ufw, so the NetworkPolicy, not ufw, is what admits VPN phones
  there (see the firewall role's header comment).
- **Keys**: the server key is made on the Pi and never leaves it. A
  device's private key is generated by `wg-peer add`, put in its QR code
  and not stored. Each device also gets a preshared key.

## Adding and removing devices

From a terminal on the home network (`-t` so the QR code draws):

```sh
ssh -t joe@192.168.1.253 wg-peer add joseph-iphone          # QR code for the WireGuard app
ssh -t joe@192.168.1.253 wg-peer add joseph-laptop --text   # config as text, for a laptop
ssh joe@192.168.1.253 wg-peer list                          # who, address, last seen
ssh joe@192.168.1.253 wg-peer remove joseph-iphone          # revoked at once
```

On the phone: install **WireGuard** (App Store / Play Store), tap **+ >
Create from QR code**, scan, allow the VPN profile. The phone also needs
the homelab CA trusted for `cam.home` to open without a warning
([https.md](https.md)). Turning on **On-Demand** in the tunnel's settings
(cellular and other Wi-Fi, not home Wi-Fi) makes it connect by itself.

**Other people don't need this any more**: since the public link
([cam.md](cam.md), "Sharing by link"), an invite link alone works anywhere.
The VPN stays for your own devices, and for anything that should never be
public.

A VPN account and a camera account are separate: `wg-peer` lets a device
reach the camera; the cam.home invite lets a person sign in to it.

## Applying it (on the Pi)

```sh
cd ~/apps/homelab/ansible
ansible-playbook playbooks/site.yml --tags vpn --limit pi --check --diff -c local
ansible-playbook playbooks/site.yml --tags vpn --limit pi -c local
```

## How it was checked

Before any phone, from a throwaway client on the Pi itself: a WireGuard
interface created in the main namespace (so its UDP socket reaches
`wg0` like a phone's would) and moved into a network namespace, with an
in-memory key and a live-only peer at 10.8.0.250 on `wg0`. Through it, on
2026-10-02:

| Check | Result |
|---|---|
| Handshake | after 5.1 s (the first initiation was lost; WireGuard's 5 s retry got it) |
| DNS `cam.home` over UDP and TCP | 192.168.1.253 |
| `https://cam.home/login`, certificate verified | 200 - through Traefik's NetworkPolicy from 10.8.0.250 |
| UDP to the Mac's 8189 | forwarded, and counted by the MASQUERADE rule |
| The desktop's Ollama (192.168.1.131:11434) | blocked by ufw - not in the forwarding rule |

What that can't cover is the router's port forward and a real phone's
WebRTC session - those need a phone on cellular, not yet done.

Also checked after applying: the ufw diff was exactly the three new rules
(plus ufw's own IPv6 copy of the 51821 one), the NAT diff exactly the
MASQUERADE rule, flannel still on 51820, both nodes Ready, and a second
run reported `changed=0`.

## Limits

- **The home IP can change.** `wireguard_endpoint` is the connection's
  public address (66.215.85.224 on 2026-10-02). If Spectrum changes it,
  phones can't connect until it's updated there, the role rerun, and the
  phones re-added. A dynamic-DNS name would remove that; not set up yet.
- **The Pi is the only way in.** If it's down, so is the VPN - and DNS,
  and the cluster's control plane, as before.
